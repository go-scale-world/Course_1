# EPR Agentic AI Course Plan (Condensed)

## Table 2: 8-Week Plan

| Wk | Skill Topic | What Will Happen This Week | What the Lab Covers | What It Adds to the EPR System |
|---|---|---|---|---|
| 1 | Introduction to Agentic AI and Models & Enterprise AI Landscape and Data Foundations | The student is introduced to what LLMs and agents are and how agentic behaviour differs from a normal API call. A raw, messy support ticket goes in and a clean structured result comes out. The student also looks at how agentic systems are already used in enterprise support and ops, and maps EPR against those patterns. Tickets stop disappearing after processing. | A Python script calls Gemini on each raw ticket and returns JSON with product area, urgency, region, and confidence. A batch pipeline pulls tickets from cloud storage, validates against a schema, and writes to raw, results, and audit log tables. | EPR can take any ticket, short, vague, or angry, and consistently return a complete, correctly structured result. EPR also persists every ticket and result. Nothing disappears silently, and every failure can be traced to the exact ticket and stage. |
| 2 | Semantic Understanding through Embeddings & Autonomous Tool Use and Event-Driven Pipelines | The system starts recognising that two differently worded tickets describe the same problem. The pipeline also stops needing a human to trigger it. It runs on its own as soon as a ticket arrives. | Ticket descriptions are embedded and stored in a vector index. New tickets match to an existing cluster or start a new one. The model is given tools such as cluster history and known issue lookup that it calls on its own. Pub/Sub triggers the pipeline on every submission. | EPR groups related tickets into shared clusters, each with an ID, description, count, and inventory. EPR is also fully event driven. No manual trigger is needed, and the model can pull extra context mid process when required. |
| 3 | Stateful Memory with Firestore & Guardrails and Enterprise Safety | Each problem group gets a status that updates on its own as new tickets arrive. The system also learns to defend itself. Suspicious or manipulative tickets are stopped before they can cause damage. | A Firestore document tracks ticket count, arrival rate, regions, and customer types per group. Every update is also archived. An input classifier blocks injected instructions. An output validator checks results. Every cluster waits in a human approval queue. | EPR maintains a live state per problem group. Counts and growth rates update automatically instead of needing a manual check. EPR also protects itself from malicious input, and every action is logged with a timestamp and actor. |
| 4 | Deployment and Human-in-the-Loop Interfaces | The pipeline becomes a live service, and a human can now watch and control it from a browser instead of a terminal. | The pipeline is wrapped in an API, containerised, and deployed to Cloud Run with automatic redeploy on every push. A Gradio dashboard shows clusters and supports approve or reject actions. | EPR is now a reachable live service with a working control panel. Approvals or rejections update the system immediately. |
| 5 | Multi-Agent Orchestration and Parallel Scoring | The single pipeline splits into a set of specialised agents that hand off work to each other, and can now handle many tickets at once while prioritising the urgent ones. | The system splits into Extract, Cluster, Score, and Escalate agents, sequenced by Cloud Workflows. Tickets are ingested in parallel and scored as Low, Medium, High, or Critical based on historical growth patterns. | EPR runs as a coordinated multi-agent workflow with a full execution log, and processes tickets at scale while flagging unusual spikes as Critical. |
| 6 | Enterprise Tool Integration via MCP | EPR starts pulling context from company Drive on its own, and drafts documentation, emails, and chat messages once something is approved. | Tool servers are deployed for Drive, Docs, Gmail, and Chat. Agent 2 queries Drive on every new cluster, and Agent 4 writes a Docs summary, Gmail draft, and Chat post on approval. | EPR is enriched with historical context on every cluster, and produces documentation, communication drafts, and notifications automatically on approval. |
| 7 | Advanced Retrieval Augmented Generation & Pipeline Automation and Observability | Retrieval becomes far more precise. The right past incident surfaces even when several loosely related ones exist. The platform also starts maintaining itself. Failures get isolated instead of stalling the whole system, and every action becomes visible on a dashboard. | Incident documents are re-indexed by section such as timeline, root cause, and resolution, tagged by severity and product area. Retrieval combines semantic and keyword search, with a scorer keeping the top three matches. A nightly pipeline indexes new Drive documents. A dead letter queue captures tickets that fail three times. Every agent and tool call logs timing, status, and errors. | EPR retrieves highly relevant past incidents for every cluster, ranked by relevance and enriched with resolution ownership details. EPR also indexes new documents on its own, isolates failed tickets safely, and makes every workflow action observable through monitoring and logs. |
| 8 | Model Fine-Tuning for Enterprise Context & Capstone and Production Readiness | The model is adapted to the organisation's own language and terminology, and compared against the base model. The full system also runs end to end in one session, and gets proven under real load. | Gemini is fine-tuned on 150 to 200 company tickets and deployed as a separate endpoint. It is benchmarked field by field against the base model on 30 held-out tickets. All layers run live. Ten tickets go in, a cluster forms, ops approves, a Chat alert fires, and a Gmail draft appears. Architecture doc, cost audit, and red team review are submitted. The system is load tested at 10,000 tickets per hour. | EPR recognises internal product names, team references, and domain specific terms more accurately than before. EPR also moves tickets from submission to approved escalation in a single flow, supported by documented architecture, cost analysis, and a written up fix for the first bottleneck found under load. |

## Capability Milestones

**Weeks 1 to 3, Structured Data Intelligence**
The student is now capable of designing systems that convert unstructured, real-world input into clean, structured, and persisted data. This includes handling inconsistent or messy inputs reliably, validating them against a schema, and ensuring nothing is lost or left untraceable.

**Weeks 4 to 5, Real-Time Autonomous Response**
The student is now capable of building systems that recognise patterns across incoming data, act on their own without manual triggers, maintain live state as new information arrives, and defend themselves against malicious or malformed input.

**Weeks 6 to 8, End-to-End Enterprise System Delivery**
The student is now capable of delivering a fully deployed, multi-agent, tool-using system with a human-in-the-loop interface, one that integrates with enterprise tools, retrieves and applies relevant context automatically, monitors its own health, adapts to domain-specific language, and holds up under real production load.
